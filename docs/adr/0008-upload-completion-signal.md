# 上传的完成信号由调用方断言

`#20` 把数据面定成按路径的文件面之后，文件面上只有 `upload` 是**两方操作**：控制层把预签名 PUT 交给调用方，**字节由调用方直连对象存储**推进中转区，而这一跳我们看不见（`#14` 的纪律：字节不过控制层）。`ls` 走流、`download` 是 Worker 搬完才回 URL、`push_workspace` 同样一手交钱一手交货——它们都是回包即结果，只有 `upload` 缺一个「Worker 怎么知道字节传完了」的钩子。`#23` 走查中转区时把它记成 `#20` 未定的缺口（`#25`）。

`#25` 决定：**`upload` 是两阶段的平台动作，第二阶段的触发来自调用方的显式断言。**

1. `upload(paths)` → 每条路径一张预签名 PUT 租约（键不透明，`#23` §四），**不触发任何搬运**；
2. 调用方自己 PUT；
3. **完成调用**（同一批 `paths`，不带任何批次标识）→ 控制层按 `(workspace_id, path)` 取该路径**最近一次铸造**的键，铸 GET 租约（一对象一张，`#12`）经**已拨通的流**下发给归属 Worker → Worker 在宿主侧拉进工作区树 → **同步阻塞**返回逐路径结果。

判据是**谁知道什么**：「这个对象存在」原则上是可观测的（控制层持平台长期凭据、能列暂存前缀，`#23` §二），但「**我这批传完了**」只有调用方知道——而 `#20` 要的是逐路径成败（「绝不静默降级」「半截文件不能当成功」）。断言只能来自唯一持有这份知识的那一方。

**Status**: accepted（`#25`）

## Considered Options

- **签发 PUT 时就下发拉取，Worker 轮询那个键直到出现或 URL 到期**（`#25` 的候选 B）：调用方只调一次，控制层零状态。否决理由：它把上传变成纯异步，调用方**拿不到任何成败信号**，只能靠 `ls` 探——与 `#20` 的失败语义正面相抵；同时它让 `#23` §三那条承重差值（对象比 URL 活得久）买来的东西作废：轮询一旦错过 URL 寿命，调用方只能重传。
- **同一批 `paths` 再调一次 `upload`，第二次调用触发拉取**（候选 A）：动词仍是三个。否决理由：同一个动词、同一批参数要表达两种语义，只能靠隐式状态判定，于是**重试与重签不可分辨**——调用方「再来一次」会铸一批新键指向空对象，把一次本可免费重试的失败变成一次必然失败。省下的那点表面整洁，代价是一个说不清的动词。
- **平台观存在**（`upload` 退回一个批次资源，控制层盯那批键何时齐了再派拉取，调用方查批次状态）：不需要调用方做第二次判断，也不会漏报「某条路径压根没传上来」。否决理由：要多造一个对外资源类型 + 一个盯存储的看门狗，买到的只是「调用方少一次调用」；**事件驱动的变体**（对象存储的 bucket 通知）从未进过我们的能力清单——`#23` 已因同一理由否掉 bucket lifecycle，不重复犯。
- **完成信号由控制层从存储侧观测**（轮询暂存前缀判断对象是否出现）：与上一条同族，且同样答不了「批次」——对象存在不等于「这批传完了」，而一次 `upload` 声明的路径集合正是批次的定义；绕一圈还是得回到「这一批是谁声明的」。
- **给「对象不在」一个短宽限**（完成后立刻拉、404 就退避重试几秒）：防「调用方刚 PUT 完，存储侧还看不见」。否决理由：**前提不成立**——rustFS 官方文档虽**全站没有一致性声明**（187 页逐页搜过），但仓库内 `docs/architecture/erasure-coding.md` 写明 PUT 在 `write_quorum = data_blocks (+1 if data==parity)` 处提交、GET/HEAD 只需 `read_quorum = data_blocks`，即 `write_quorum ≥ read_quorum`：健康集群上**已提交的 PUT 对随后的 GET/HEAD 可见**（PR #4703 亦自称 strong read-after-write；AWS 侧官方文档明写 strong read-after-write consistency，含 HEAD 元数据）。于是 404 就是「真的没到」，退避重试只会把一个确定的答案拖慢。真正的故障窗口是另一回事（见 Consequences）。
- **落地成功即删中转对象**：落地现在虽然可观测了（Worker 回报逐路径结果），技术上挂得住。否决理由：它把「失败的搬运不需要调用方重传」削掉一半——调用方丢了一次回包、要幂等重拉时对象已经没了。回收继续纯时间驱动，`#23` 一字不改。

## Consequences

- **`#20` 的「三个动词」变成四个**（第四个动词的名字与端点在 `#17` 收口）。**实质不变**：文件面只管进出，不设 mk/rm/mv/chmod；面上的一个操作仍一对一映射控制层的一项操作（`#15`）。
- **等待形状与 `push_workspace`、`download` 三者同形**：同步阻塞、无服务端上限、由客户端超时决定。`#18` 的长轮询是给「状态活在控制层里」的 task / logs 用的；搬运的回包本身就是结果，把它切成 60 秒一片只会让一次 5GB 的拉取变成轮询 N 次拿同一个答案。
- **解析规则**：完成调用传 `paths`、不引入批次标识，代价是**同一 `(workspace_id, path)` 上后铸的 PUT 租约取代先前的**。于是「重铸了却没 PUT」会让那条路径按「对象不在」**大声失败**（不是静默错），且重试路径最短：重传＝重走 `upload`（重铸 → PUT → 完成），对象还在（1h）时**重发完成调用＝重拉**。
- **失败语义**：逐路径结果 `{path, ok, size?, code?}` 走 200（成功时必填 `size`——调用方手里有自己刚 PUT 的字节数，这条让「半截文件不能当成功」它自己也核得动）；整批级错误只有两个：签发阶段的 `invalid_argument`（路径校验在**签发**时做完，不拖到落地）与归属 Worker 不在的 409 `workspace_unavailable`（`#18` 现有码）。「这条路径从没签过」与「签了但对象不在」是两个码——前者是调用方的流程 bug，后者可重试；最终措辞归 `#17`/`#18`。
- **落地侧的规矩**（`#20` §五三条死规矩在上传方向的镜像）：父目录**自动建**（`mkdir -p` 语义——树里没有 mkdir 这个动词，否则调用方得先提一个 Task 去建目录）、**原子落地**（同目录临时名 + `rename`，树里永不出现半截文件）、**逐段不跟随符号链接**（树里一条 `src -> /etc` 会让落地 `src/passwd` 变成宿主写盘；实现建议 `openat2(RESOLVE_BENEATH)`）、只处理普通文件、覆盖既有文件。
- **「对象不在」与「存储侧说不清」必须分开说**：rustFS 的一致性论证有一条故障注脚（PR #4597／issue #2761）——新对象在 heal 前只落在 `write_quorum` 块盘上，此窗口内一次瞬时的 peer reset 会返回 `InsufficientReadQuorum`（**HTTP 503，永不是陈旧数据**），rustFS 自己给了 `RUSTFS_INTERNODE_IDEMPOTENT_READ_RETRIES=1` 这个有界重试开关。所以：**404 ＝ 这条路径真的没到**（逐路径 `object_missing`，可免费重试）；**存储侧 5xx ＝ 瞬时故障**（Worker 侧一次有界重试，与存储自带的那个开关同形；仍失败则整批 503 `unavailable`，对象还在、重试免费）。**绝不把 503 说成 `object_missing`** —— 这就是 `#20`「绝不静默降级」在存储故障上的具体兑现：说得出「我说不清」与「我知道它没到」的区别。
- **URL 与传输时间的耦合是具名天花板**：调用方那次 PUT 的传输时间被预签名 URL 寿命（默认 15 分钟，`#23` §三）封顶。内网 5GB @50MB/s ≈ 100 秒够用；慢链路上的大对象 PUT 必中途失效且不留痕（单键原子），只能重铸重传。升级路径是 multipart（`#20` 已留，且必须一并带 abort，`#23` §七），或给上传方向单独放宽 TTL。
- **「上传完再提交任务」成为调用方的次序自律**：完成调用不进 Task 串行（`#20`：平台动作不占任务位），所以平台不保证下一个 Task 看见刚上传的文件。Skill 那句「要留下的东西放进工作区树」旁边要再加这一句。
- Worker 侧拉取在**进程内**用 URL 直连——不 exec、不进 argv、不落盘。依据是 `0001` 的 Consequences：「宿主上执行的换发必须把凭据留在进程环境里，**绝不进 argv**（`/proc/<pid>/cmdline` 是同机任何用户可读）」；预签名 URL 就是租约的 secret，因此它走 HTTP 客户端而非命令行。
- **`download` 与 `push_workspace` 无同类缺口**（核对结论）：`download` 是 Worker 搬完才回 URL，回包即落地；`ls` 与 push 无字节过存储。文件面上仅有的两处「调用方拿 URL 直连存储」（upload 的 PUT、download 的取走）都不可观测，后者已由 `#23` 的时间驱动扫帚收掉。
