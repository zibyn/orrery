# 中转区：无主对象，按保留期回收

`#20` 把数据面改成按路径的文件面之后，平台存储里多出一类**无主**对象：两个方向都要在这里过一手——上行走 `upload` 的字节（调用方 PUT 进来，等 Worker 拉进树），下行走 `download` 的树内文件（Worker 推上去，等调用方取）。它们不属任何 Task（文件面与 Task 无关）、不属任何产物清单（产物已随 `#7` 废除）、也没有「谁授权了它」这个问题（`#14`：平台自有存储是系统自持的）。`#23` 决定：回收**纯时间驱动**——控制层按 `<staging>/<workspace_id>/` 前缀扫、超期即删；**单一保留期**（对象默认 1 小时）且**长于预签名 URL 的寿命**（默认 15 分钟）；对象键**不透明**；**不记账**。

**Status**: accepted（`#23`）

## Considered Options

- **按「搬运完成」回收**（Worker 拉完就删 / 调用方取完就删）：**机制上不可能**，这是本决定的地基而不是一个被权衡的选项。① 预签名 URL 一个对象一个方法（`docs/research/s3-short-lived-authorization.md` §1.3 原文：「一个预签名 URL 只对一个 object + 一个 HTTP 方法有效」），所以手里那个 PUT 的 URL 删不掉那个对象；② 下载方向的「取走」**在我们这侧不可观测**——调用方拿着 GET URL 直连存储，字节不经过控制层（`#14` 的纪律）。没有任何事件可以挂回收，于是回收只能由时钟驱动。
- **存储层的桶生命周期规则**（前缀上挂 Expiration）：零簿记、零新机制，是平台原生能力，本该优先。否决理由有二：**它的精度是「天级且不保证」**——AWS 原文是「Amazon S3 把规则里的天数加到对象创建时间上，**向上取整到次日 00:00 UTC**」，而且「生命周期规则被满足与该动作完成之间有延迟……**S3 不保证 transition 或 expiration 的完成时间**」，官方自己写着「不建议单独依赖 S3 Lifecycle 处理有固定期限的删除」。一块本该活一小时的空间会活到一天甚至更久，那正是本票要封的界，等于把这个界放大 24 倍以上。其次，它在 rustFS 上的支持面**从未进过我们的能力清单**（§2.1 列了 bucket CRUD / bucket policy / object tagging / presigned GET·PUT，**没有 lifecycle**）。若将来实测证实支持，它可以当清扫器挂掉时的第二道——但规格不依赖它。
- **把 TTL 定成「产物」那种量级**（30 / 90 天，GitLab·Buildkite·CircleCI 的默认值）：**类比错了**——那些是**产物**（一次构建的留档，用户会回来取），这里是**搬运途中的一份副本**，两个方向都能随时重做（上行重传、下行重 `download`）。沙箱厂商给自家存储对象设的 TTL 明显更短（Cloudflare Sandbox 备份 3 天、Daytona 预签名 URL 默认 3600 秒），1 小时落在搬运这个场景里。先例也支持「TTL 写在自家对象上不自动等于会被清」这条警惕：Cloudflare 的备份 TTL **只在 restore 时校验**，对象实际留在 R2 里直到有人删或另配 lifecycle 规则——我们不接受这种「写了 TTL 但不执行」的形状。
- **记账**（把中转对象并进 `#11` 的「保留期全额占账」）：**记错了池子**——一个是宿主磁盘、一个是对象存储，中转对象不占 Workspace 的 `resources.disk` 预留。中转区不是无界的（见 Consequences），而给人一块不存在的磁盘上账，会让调度器的容量账出现静默偏差。
- **按 Task 切前缀**：做不到——文件面与 Task 无关（`#20`），三个动词里根本没有 `task_id`。
- **对象键用树内路径**（`<staging>/<workspace_id>/<path>`）：看起来按路径寻址更对称，但调用方给的路径是**不可信输入**，编进存储键就得管编码、穿越与长度，还会被带进存储侧的访问日志；而调用方**不需要**预测键（它拿的是 URL，Worker 经流拿的是键）。不透明 id 让这条输入校验面整个不存在。

## Consequences

- **中转区的容量上界 = 一个保留期内发生过的搬运总量**，不是零。调用方可以在窗口内反复上传把这块填满——这是**具名天花板**，不是疏忽。真要防，加的是「每 Workspace 的中转并发/字节上限」，不是记账。
- **对象比 URL 活得久**，这条差值是承重的：它让「换个 URL 再取一次」（`#14` 的「可重复换取」）与「Worker 拉取失败后重拉」成立——失败的搬运**不需要调用方重传**，只要对象还没到期。
- **前缀按 Workspace 切，与 `#5`/`#14` 留的升级路对齐**：将来整目录搬运要退回 **prefix 级 STS 会话**时，会话策略指到 `<staging>/<workspace_id>/` 即可，布局一行都不用改。
- **中转对象的寿命与 Workspace 生命周期无关**：`DestroyWorkspace` 不连带清它（联动会造出第二条回收路径、两套时序，还要处理「删到一半 Worker 正在拉」）。因此销毁之后，调用方手里未过期的 URL 仍取得走——**那只是「还没到期」，不是泄漏**：对象是它自己传进去的，或它自己树里的。
- **失败残留收敛成一条规则**：半截上传**不留东西**——预签名 PUT 按 key 是原子的（S3 语义：「对单个 key 的更新是原子的……绝不会读到部分或损坏的数据」），而 v1 没有 multipart；将来上 multipart 必须**一并**带上 abort 机制（未完成的分片不会被普通过期规则清掉，要专门的 `AbortIncompleteMultipartUpload`/预签名 DELETE，先例见 GitLab Workhorse 的 `AbortURL`/`DeleteURL` 与 Blaxel 的 `abortUrl`，见 `docs/research/vendor-file-apis.md` §Blaxel）。「URL 从没被用过」与「对象被拉完但没删」则由同一个保留期收掉。
- **本票挖出一个 `#20` 未定的缺口**：`upload` 之后**谁、什么时候告诉 Worker 去拉**（控制层看不见调用方的那个 PUT），以及调用方**从哪里拿到完成信号**。回收结论不依赖它（纯时间驱动正是为了不依赖），但它牵动对外 API 的调用形状与错误面 → 新票，阻塞 `#17`。
