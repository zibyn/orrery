# 能力面是控制层操作的薄映射

能力面（MCP 工具 / CLI / Skill）**不新造语义**：面上的一个操作，一对一映射到控制层的一项操作，参数同源、命名同源、失败面同源。三个面是同一个 `stars-sandbox` 二进制的不同入口，共用同一个客户端库、走控制层同一套对外 HTTP/JSON（`#18`）；**CLI 是全集，MCP 是它的子集**（管理面——签发登记包、撤销/下线 Worker——只在 CLI），**Skill 是文档，不承载能力**。由此两条推论最容易被日后侵蚀，写死在这里：**没有复合工具**（不存在「建工作区→跑命令→等终态→取日志」那种 `execute` 入口）、**没有文件面**（面上不存在「读/写某个路径」，文件进出走 `/inputs` 的目录同步与按名声明的产物）。

**Status**: accepted（`#15`）

## Considered Options

- **一个粗粒度 `execute` 工具包办生命周期**：对模型省往返，但它只能把可裁决的失败压成一个黑盒返回——`#7` 的 Task 是带幂等键、ack、绝不自动重试的完整信封，`#9` 是显式两步，`#11` 放不下立刻 `NoFit`，`#14` 产物先声明后取回。复合工具等于在能力面上重造一套重试/超时/等待语义，而重试归调用方是 `#7` 定死的。往返成本改用两个薄工具吸收：`submit_task` + `wait_task`。
- **能力面提供文件读写**（`read_file` / `write_file`）：外层智能体手感好，但把 `#10` 的「文件读写不进接口」（沙箱不可能是数据的家）重新打开，数据面从声明式同步退化成逐文件 RPC。
- **能力面不碰远端动词**（原推荐：外层只提交一条跑 `git push` 的 Task）：更贴合「工作区里干活的代码才发起远端动词」，但外层调用方就得复述仓库坐标与凭据知识——正是 `#12` 要挡的——而且外层将无从知道改动是否回到仓库，除非任务自报。

## 关于 push

`push` 是能力面上的一个**平台动作**，不是 Task、也不在 Task 信封上加字段：调用方只给 `workspace_id`，控制层解析它的仓库引用（`#13`）→ 授权 → 让归属 Worker 铸租约（绑 `workspace_id`、`task_id` 缺席，`#12`）→ 宿主侧代发。它与沙箱内 shim 的 push **共用同一个 Worker 侧代发器与同一种租约**，只有触发面不同——这条不变量是防止两条路径日后漂移出两种语义的唯一保障。push 不要求 Workspace 空闲、不占任务的位置、不进任务串行；失败**大声失败**（`Denied` / `Unavailable` / 非快进被拒）并带一段有界输出；**force-push 不另设开关**——refspec 里带 `+` 即是 force，授权早在 Grant 上判过（`#13`）。

## Consequences

- 工具集由**操作集**决定，不由「模型好不好用」决定：加一个工具等于控制层多一个操作，不能是能力面自己攒的复合动作。
- 外部调用方自己持有幂等键与重试（`#7`），且「跑点东西」至少两次往返——这是 `#9` 显式两步的直接代价；嫌贵该改 `#9`，不是在能力面上补一层糖。
- MCP server 只是同一个二进制的 stdio 模式，与管理面共用同一套对外鉴权（`#18`），**不开特权路径**。
