# Worker 的部署与升级：一个二进制的两个入口，升级不上线

控制层与 Worker 这层关系里，只有一处**必须**由软件承担——协议代际的窗口。因此本 ADR 记下两条容易被日后"顺手"改回去的选择。**部署件**：一个 distroless 单二进制 + 宿主 systemd 单元（rootful），**同一份二进制兼任 netns nftables 的 OCI hook**（`stars-sandbox oci-hook`）——hook 与 Worker 于是没有版本关系可言，偏斜在形状上不可能，升级只有一个产物要换。**升级**：不由控制层编排——控制层只持一个旋钮，**全机队的最低可接受协议代际，且双向可动**；期望版本不上线（Worker 不自我更新，那会是一根没人读的字段）、灰度批次复用**放置标签**。二进制怎么发、按哪个批次滚、什么时候回退，是运维动作。

闸门是**代际**（一个小整数，即 `StreamWelcome.protocol_version`）而不是二进制 semver；协商点在流之外——开流时 `protocol-generation` 走 gRPC metadata，控制层在发任何应用消息之前裁决，窗口外直接 `INCOMPATIBLE` 关流，因此不兼容的情形不会开出一条要收尾的半开流。不兼容是`#6`那张失败语义表的**第三类**：不自清、不无限退避，保留身份、拒接活、固定慢节奏重试并持续大声报错——于是**控制层回退即可自动治愈整个机队**。Worker 只说自己那一个代际，控制层必须说得出口窗口内每一代。升级不排空：`SIGTERM → 换二进制 → systemd 拉起 → 收养`，用的全是 `#8` 已经建好的零件（`GoingAway` 的 draining、`StreamWelcome` 派发闸门、重启后尽力收养）。

**Status**: accepted（`#19`）

## Considered Options

- **控制层全编排升级**（期望版本下发 + Worker 自取二进制 + 自替换 + 批次 + 回退）：把控制层变成制品仓库加一个自更新守护进程。分发点其实可以复用平台自有存储 + 预签名 URL（`#14`），所以它不是不可行，而是**为内网小机队付一份没人要的复杂度**——自更新要重新发明「换正在运行的二进制、systemd 重启、版本回退」三件事。
- **只上报版本、不做代际窗口**：代价是每次动协议全机队停机，而协议现在还年轻、会常改。
- **闸门用二进制 semver 范围**：范围匹配是纯增的复杂度，且没有先例——GitHub 是硬地板（低于 `2.329.0` 不能注册），GitLab 是带日期的窗口（15.6 宣布 → 17.0 `410 Gone` → 移除滑到 20.0）。
- **把关口放在首条心跳或续期响应里**：Worker 可能开着一条 12 小时的流，记在 Worker 行里的代际会陈旧；绑在续期上则意味着想提前收窗口还得等下一个续期周期。
- **灰度批次做成控制层字段**：窗口是控制层的能力，批次是运维的选择；混在一起，控制层就得实现发布编排。
- **先排空再升级（cordon）**：要新增「控制层尊重 drain 标签」的语义（改 `#11` 的调度器）＋运维多一步等待，而 `#8` 的 `GoingAway` + 收养 + 派发闸门已经就是这条路径。
- **包管理器分发（deb/rpm）**：内网没有 repo，且会把「二进制在哪」变成第二个真源。
- **把 Worker 也容器化**：它要的是 docker socket、netns、CDI 设备与宿主上的 Workspace 目录——容器化只是给自己套一层需要逃出去的边界，而先例里自拨号 worker 全是宿主进程。

## Consequences

- **升坏一台 Worker = 它名下所有 Workspace 一起 `WORKSPACE_UNAVAILABLE`**：Workspace 机器绑定（`#9`）＋ Workspace ↔ Sandbox 1:1，没有替代机器可去。所以灰度批次的选择标准是"这些机器上的 Workspace 暂时丢了也不要紧"（备注：1:1 与机器绑定决定了灰度批次的选择只能按"容忍丢失"来选）。
- **窗口的宽度 = 控制层还背着几代协议代码**，这是不停机升级的全部成本；下沿要有生效时点，且必须能退回去——回退就是退回下沿，同一个旋钮。
- **发布次序固定**：控制层先行（它同时说得出口 N 与 N-1）→ 滚动 Worker → 抬下沿。控制层自身重启不打断任何任务（`#8` 的重连 + reconcile + Worker 保留身份退避），所以这一步不需要停机窗口。
- `Capabilities()` 带上 runtime 工具链的版本事实（dockerd / toolkit），低于下限报 `unsupported`（`#10` 的三值）——调度器与能力面因此天然看得见，不需要任何版本协商，也不做能力分支（照 `#13` 的纪律）。
- 控制层监听面拆成三处、各自可配地址（能力面 `/v1/`、Worker gRPC、`Enroll`），`Enroll` 默认只绑运维/装机网段，登记包加 `enroll_url`（**覆盖 `#6`**）。
- 运维需要一份**宿主前置条件清单**——systemd、cgroup v2、docker ≥ 28.3.0（CDI 默认开启）、nvidia-container-toolkit ≥ 1.18.0（要 `nvidia-cdi-refresh.service`）、nftables + netns、`/var/lib/stars-sandbox/` 的路径与权限、`/etc/machine-id`。它与"升级是运维动作"是同一件事的两面。
- 两处事实本 ADR 无法覆盖，仍是空白：CDI spec 的版本号、跑 GPU 容器的最低驱动版本（现有来源里只有 MIG / MPS 各自的门槛）。
