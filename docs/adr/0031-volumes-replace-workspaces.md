# ADR-0031: A Sandbox's whole filesystem persists and moves between Nodes, and Volumes on object storage replace Workspaces

- Status: accepted (2026-11-17, after `docs/research/runsc-rootfs-visibility-spike.md`); amends in place ADR-0009's `Stop` ("never deletes the Workspace"), ADR-0012's publish, ADR-0014's Node loss, ADR-0015's "Workspace", ADR-0017's "Workspace" and `node_lost` cascade, ADR-0018's "Ephemeral Workspace" and "Files go through a ready Sandbox", #220's read-write mount and ADR-0030's Local `ORRERY_WORKSPACE`; `GLOSSARY.md` is updated; `api.md`, `schema.md`, `node-protocol.md`, `runtime.md` and `defaults.md` follow, and those ADRs carry the amendment notes; #273 is replaced by the Volume file API
- Date: 2026-11-17

## Context

A Workspace is a Node-local directory that every Sandbox mounts at `/workspace`; a Sandbox created without one gets an implicit ephemeral Workspace, because `Stop` deletes the whole Runtime and only the Workspace survives (ADR-0009, ADR-0018). Both the Workspace and the Sandbox are bound to one Node for life (`workspaces.node_id`, and `sandboxes.node_id`, which is never cleared: `internal/store/queries.sql:467-470`), so a Node's loss loses them, and a stopped Sandbox cannot start anywhere else. Every Sandbox appears a second time in the Workspace list, the Workspace page cannot show files without a ready Sandbox, persistent Workspaces are placed on the first ready Node regardless of GPU or capacity (`internal/api/reconcile.go:486-503`), provisioning is a retried state machine around one `mkdir` (`internal/agent/runtime.go:248-259`), and read-only mounts expose a live directory a writer may be changing. Packages installed outside `/workspace` are lost on every stop.

Research found that no sandbox platform makes every sandbox mount a separate entity: each sandbox has its own filesystem, and a volume is an optional extra (`docs/research/workspace-model-weight-audit.md` §1). Daytona keeps the whole container filesystem across stop, commits it on stop and hourly, and restores it on another runner when one is unavailable; E2B keeps the whole rootfs as block diffs in object storage and restores it anywhere. Both offer Volumes on object storage that are not bound to a machine, and both say Git and builds belong on the sandbox's own disk, not on a volume (`docs/research/workspace-cross-node-and-git-storage-vendor-practice.md` §1, `docs/research/code-vs-training-data-vendor-practice.md` §1.2, `docs/research/daytona-sandbox-runtime-semantics.md` §1.6). A FUSE filesystem made `git clone` about 12 times slower than a host directory (`docs/research/workspace-wsfs-fuse-spike.md`). Under runsc's default `overlay2`, root filesystem writes are hidden from the host in one opaque `.gvisor.filestore.*` file; with `overlay2 = "none"` they land as ordinary files in containerd's upperdir, at the speed `/workspace` has under runsc today (`docs/research/runsc-rootfs-visibility-spike.md`).

The direction was chosen on 2026-11-17: follow Daytona and E2B; persist the whole filesystem rather than `/workspace` only; Volumes mounted by one Sandbox at a time; no read-only mounts.

## Decision

**A Sandbox's filesystem is the Sandbox's.** Everything a Sandbox writes to its root filesystem, installed packages and `/workspace` alike, survives stop and start and is deleted with the Sandbox. It is the diff of the container's upperdir against the Sandbox's SnapshotVersion, which therefore stays fixed for the Sandbox's life. `/workspace` is an ordinary directory, created empty at first start when the image lacks it, and stays the default working directory. There is no Workspace, ephemeral or persistent, and no separate disk entity.

**Generations.** The filesystem is persisted as Generations: immutable states of the diff in object storage. A Generation's manifest records each changed path with its type, full mode, owner, mtime, extended attributes, hard links, and the overlay whiteouts and opaque directories that express deletions from the SnapshotVersion; content is stored as CAS objects in ADR-0030's layout (one object up to 4 MiB, 4 MiB blocks beyond), deduplicated per owner (ADR-0021). The Agent commits by stat-scanning the upperdir against the last Generation's table and uploading only changed files (`workspace-shared-storage-s3.md` §4.6), skipping `*.lock` inside Git directories (`workspace-cross-node-and-git-storage-vendor-practice.md` §4.3); the Control Plane verifies the objects and advances the Sandbox's head Generation in one transaction that checks the Sandbox's `generation` fence. Only the head and Generations a pending publish references are kept; the rest are collected by the CAS sweep.

**Commit on stop.** `stopping` ends only when the commit succeeds; the Agent keeps the container snapshot until then and retries with backoff, showing `commit_stalled`. A commit that cannot succeed (the upperdir unreadable) fails the Sandbox with `commit_failed`, and the Node's copy stays until the Sandbox is deleted. Periodic commits while running, a `checkpoint` API and Generation history for Users are deferred; the formats above allow all three.

**Any Node can start a stopped Sandbox.** `sandboxes.node_id` becomes the Node that last ran it, kept as a placement preference, not a constraint: admission places a starting Sandbox on any feasible Node, preferring the one whose cached diff equals the head. Elsewhere the Agent restores the head into a fresh upperdir over the SnapshotVersion, fetching only objects missing from its CAS cache, before it starts the Runtime; restore time grows with the diff, and lazy restore is deferred. A Node's cached diff of a stopped Sandbox is evictable under its disk watermark once the head equals it. On a Node's loss, its running Sandboxes become `stopped` with cause `node_lost` and a `changes_lost` condition instead of `failed`, and start again elsewhere from their last Generation, or from the SnapshotVersion when none was committed; a Sandbox `stopping` there keeps its retry until the Node is declared lost, then does the same.

**runsc Nodes run with `overlay2 = "none"`.** The Agent writes it next to `host-uds = "create"`. Root filesystem writes under runsc cost what `/workspace` writes cost today; work that previously wrote heavily into the in-sandbox overlay, such as `git add` of thousands of files, is up to about 40% slower (spike §2). runc Nodes need no change.

**Volume.** A Volume is a named, writable directory in object storage that a User creates, mounts into Sandboxes and deletes explicitly; it is bound to no Node. `POST /volumes {name}` creates it (the name is unique among the owner's non-deleted Volumes); `GET /volumes`, `GET /volumes/{id}` and `DELETE /volumes/{id}` (refused while mounted) complete it, with `POST /volumes/{id}/publish`. Its states are `ready` and `deleted`: deleting one needs no Node, and its objects are collected by the CAS sweep. A Volume is persisted as Generations of the same format; its content is the whole tree, not a diff.

**Mounting a Volume.** `POST /sandboxes` takes `volumes: [{volume, path}]`, at most 16, fixed for the Sandbox's life. A path is absolute and normalized, is not `/`, does not lie under `/resources`, `/.orrery`, `/proc`, `/sys` or `/dev`, and does not contain or lie under another mount's path; it may be `/workspace`. The Node mounts it through FUSE: `orrery-resourcefs` (ADR-0030) gains a writable mount that reads the head Generation lazily, keeps writes and metadata on the Node, and commits a new Generation every 60 seconds while dirty and when the Sandbox stops; stop waits for that commit as it does for the filesystem's. `fsync` does not wait for a commit. Writes since the last commit are lost with the Node.

**One Sandbox at a time, always read-write.** A Volume is mounted by at most one Sandbox; the Sandbox holds it from `pending` until it stops, fails or finishes deleting, as #220's read-write mount does, and starting or creating a Sandbox whose Volume another holds is a `conflict`. Because a Volume has no Node, holding it adds no placement constraint. There are no read-only mounts: a Volume's or a Sandbox's content is shared by publishing it as a Resource, mounted read-only and lazily, so a reader sees one point in time.

**Volumes are for data, not for Git.** A Volume costs FUSE's 2.5–16x write overhead; the documentation says to keep repositories and builds in the Sandbox's own filesystem, as Daytona and E2B do. The platform does not refuse Git on a Volume.

**Files and publish without a Node.** `GET /volumes/{id}/files`, `/stat`, `/content` and `/archive` are served by the Control Plane from the head Generation's manifest and presigned reads, whether or not a Sandbox mounts it; while mounted they show the last commit. There is no write route. `POST /volumes/{id}/publish` publishes a path of the head Generation as a ResourceVersion without moving data, since the objects are already in the owner's CAS. `POST /sandboxes/{id}/publish` publishes a path of a `ready` Sandbox's live filesystem through its Node, as Workspace publish did; it does not commit, because committing a running Sandbox needs the freeze that periodic commits will bring (amended 2026-11-17 while writing the spec). The file API of a running Sandbox stays under `/sandboxes/{id}/files` and now addresses its whole filesystem, rooted at `/workspace` by default.

**Local Runtime.** A Local Sandbox has no root filesystem of its own. Its persisted filesystem is its working directory, `ORRERY_WORKSPACE`, committed and restored as above; a Volume is mounted under `<data-root>/sandboxes/<id>/volumes/<name>`, a directory named by `ORRERY_VOLUMES`, because Local cannot honour a mount path.

**Migration.** An ephemeral Workspace's content becomes its Sandbox's `/workspace`: the Agent uploads it as the Sandbox's first Generation at the upgrade, and a running Sandbox keeps its bind mount until it stops. A persistent Workspace becomes a Volume with its ID and the name `workspace-<first 8 hex of its ID>`, uploaded the same way, and a Sandbox that mounted it read-write mounts the Volume at `/workspace`; its repositories then run on FUSE, so the upgrade notes say to copy them into the Sandbox. Read-only mounts are dropped. The `/workspaces` routes, the `workspace` request field, the CLI `workspace` commands and the Workspaces page are removed in the same release, and the Node protocol's Workspace messages are replaced. A Workspace that cannot be uploaded because its Node is lost is lost, as it is today.

## Consequences

- A Node's loss no longer loses stopped Sandboxes or Volumes, only what running ones wrote since their last commit; with commits only at stop and every 60 seconds for Volumes, a running Sandbox's whole session since start is at risk until periodic commits are built.
- Stop takes as long as uploading the diff; a Sandbox that wrote gigabytes stops slowly, and one whose Node cannot reach the object store stays `stopping`.
- Starting a stopped Sandbox on a new Node waits for its diff to download.
- The object store holds every Sandbox's diff, not only Resources and Snapshots; it needs capacity planning, and User Quota does not yet bound it.
- Clients calling `/workspaces` or sending `workspace` break at upgrade; there is no alias period.
- A GPU Sandbox's Volume no longer pins it to a Node, which removes the `unsatisfiable` the Node-local design produced.
- `orrery-resourcefs` becomes a writer, so its crash loses a Volume's uncommitted writes and breaks its mount until the Sandbox restarts.

## Rejected alternatives

- Node-local Volumes mounted by one Sandbox (this ADR's first draft): simpler, but neither a Volume nor a Sandbox could leave its Node.
- Persisting only `/workspace`: same mechanism over a smaller tree, but installed packages would still vanish on every stop, unlike Daytona and E2B.
- Daytona's `docker commit` to the platform registry: each commit carries the whole diff against the image as one layer, without file-level increments or per-owner deduplication, and stacking layers grows without bound.
- E2B's block-device rootfs with lazily fetched blocks: needs a VM runtime; Orrery runs containers under runc and runsc.
- Copying runsc's `.gvisor.filestore` file under the default `overlay2`: an opaque, gVisor-internal format with no increments, restorable only by runsc.
- Volumes written by several Sandboxes at once, last write winning, as in Daytona: possible later; a single writer keeps the FUSE daemon's cache and commits simple.
- Keeping read-only mounts: readers would see a live directory; Resources already give them a point in time.
- Keeping Workspaces and only hiding ephemeral ones: smallest change, but it keeps everything Node-bound.
