## 0. 先读这几条

1. **两家都没有「持久化的 Exec」。命令执行在两家都属于数据面，是临时的；持久化只做在更粗的层上。** Coder 持久化的是 workspace build（`provisioner_jobs`）；Daytona 持久化的是 Sandbox 的 `desiredState`。Coder 的进程 API（`agent/agentproc`）和 Daytona 的 session/PTY 都只活在 agent/daemon 的内存里（`C/agent/agentproc/process.go#L27-L50`、`DT/apps/daemon/pkg/session/service.go#L16`）。我们把 Exec 放进 Control Plane 的 PostgreSQL，**比两家都重**。但这一点有理由：两家都栽在同一类问题上，Daytona 的 #4520（返回 202，命令却从未执行）、#5140（daemon 死掉，沙箱仍显示 `started`，不给原因）、#5144（超时后丢掉已产生的输出）就是证据。**判定：保留「Exec 是 Control Plane 资源」，但下面三处要砍。**
2. **应简化：去掉 ExecAttempt 和自动重试。** 两家都不自动重试命令。Coder 的源码注释写的是 *"We need to mark this job as failed so the end user can retry if they want to."*（`C/coderd/provisionerdserver/provisionerdserver.go#L550-L553`）。我们的 Sandbox 绑定在一个 Node 上，又不跨 Node 重调度，所以「新 Attempt」和「同一个 Exec 再投递一次」实际上没有区别。一行 Exec，加上从时间戳派生的状态（Coder 的 `job_status GENERATED ALWAYS AS (...)`，`C/coderd/database/dump.sql#L2983-L2998`），就够了。
3. **应修改：Node Agent 重启后，正在跑的 Exec 怎么办，必须二选一。** 我们写的是「Agent 重启后由对账接管，`lost` 可以回到 `running`」，但没写输出管道怎么活下来。两家各给了一个诚实的答案：Coder 的 agent 关闭时**杀掉所有进程**（`C/agent/agentproc/process.go#L320-L323`）。Daytona 让命令在沙箱里**把输出写进文件、退出码写进文件**（`output.log` / `exit_code`），所以 daemon 换了也能接着读。Phase 1 选 Coder 那条最省事：Agent 重启时，在跑的 Exec 一律以显式原因结束。这样「`lost` 回到 `running`」的恢复路径和磁盘 spool 都可以删掉。
4. **应修改：日志溢出时不要杀掉 Exec。** #33 规定 spool 满了就以 `log_storage_failed` 终止 Exec；ADR-0014 对 PG 上限的处理却是「写一个截断帧，进程照跑」。两者自相矛盾。Coder 两处都选了截断加标记：内存队列满了截断，数据库层设 `logs_overflowed`（`C/codersdk/agentsdk/logs.go#L317-L324`、`C/coderd/database/dump.sql#L3781`），从不因为日志杀进程。
5. **应修改：Node Agent 那一条 gRPC 流不要再承载 PTY 和输出帧。** 两家都把控制通道和逐连接的数据通道分开。Coder 的控制走 dRPC，PTY 和 SSH 走 tailnet 上逐连接的流。Daytona 的控制是 runner 轮询 `/jobs/poll`，数据走 proxy 到 daemon 的逐个 WebSocket。如果全部塞进一条流，就要自己做多路复用和流控；而且一个慢的 PTY 会阻塞心跳。Daytona 自己就有「慢客户端直接被踢」的代码（`DT/apps/daemon/pkg/toolbox/process/pty/websocket.go#L20`、`#L98-L117`）。做法：控制保持一条流，每个 Exec 或 attach 由 Agent 另开一条 gRPC stream（同一个 HTTP/2 连接）。
6. **PTY 有两处与两家不同：** ①单控制者：两家都允许多个连接同时写（**应简化**）。②两家都踩过的「无人连接的 PTY 永远挂着」，我们没有防（**应修改**：加 detach 空闲超时，Coder 默认 5 分钟，`C/agent/reconnectingpty/reconnectingpty.go#L93-L96`、`#L125-L127`）。另外，PTY 输出写进 PG 也比两家都重：两家都只在节点上保留一个有界的回放缓冲，或者完全不回放。

### 1.2 #33 Exec 持久化与对账

| # | 裁决 | Coder | Daytona | 判定 |
|---|---|---|---|---|
| 33-1 | `Exec` 是持久意图，`ExecAttempt` 是一次具体尝试，两套状态机（6 个状态，9 个状态） | 命令（`/api/v0/processes/start`）只在 agent 内存里，退出 5 分钟后清掉，**没有 Attempt**（`C/agent/agentproc/api.go#L58-L61`、`process.go#L27-L29`）。唯一的持久任务是 provisioner job，**状态从时间戳派生**，不存枚举：`pending/running/canceling/canceled/succeeded/failed`（`C/coderd/database/dump.sql#L2983-L2998`） | 命令在 daemon 内存的 `cmap` 里，输出和退出码写成沙箱里的文件；没有 Attempt（`daytona-sandbox-runtime-semantics.md` §4.2、§4.6） | **应简化**：保留 Exec，删掉 ExecAttempt 和 Attempt 状态机。Exec 存 `accepted_at / started_at / cancel_requested_at / deadline_at / finished_at / result`，状态派生（照抄 Coder 的 generated column） |
| 33-2 | Sandbox 必须是 `ready`、Lease 已满足才接受 Exec，不在 Exec 里藏排队；Sandbox 停止或撤销 Lease 时，先持久化取消意图再终止 | 有构建在跑时，新建 build 直接 409（`C/coderd/wsbuilder/wsbuilder.go#L1383`） | 沙箱不在 started 时，toolbox 请求失败，而且失败形状很糟（#4142 返回 400/502） | **保留**：比 Daytona 好的地方在于有明确的拒绝码 |
| 33-3 | Idempotency-Key 防重复；相同 key 加不同请求体返回 `conflict`；Attempt 有稳定 id，Agent 对投递和启动做幂等 | 无 | 调用方 cmdId 冲突返回 409 | **保留**前半句（见 31-6）。**后半句随 33-1 简化**：投递幂等的键就是 `exec_id` |
| 33-4 | 只对明确尚未交给 Provider 的瞬时基础设施错误自动重试，最多 3 次；启动结果不确定就标 `lost`，不跨 Node 重调度 | 不自动重试：*"mark this job as failed so the end user can retry if they want to"*（`C/coderd/provisionerdserver/provisionerdserver.go#L550-L553`）；卡住的 job 由 reaper 直接判失败（`C/coderd/jobreaper/detector.go#L21-L40`） | 不重试命令 | **应简化**：Phase 1 不自动重试。预启动失败直接以可重试的错误码 `infrastructure_unavailable` 结束，由调用方（Agent）决定是否新建 Exec。`prior-art` §4.4 已经得出过「重试要显式 opt-in」 |
| 33-5 | `lost` 可以由对账恢复：确认仍在跑就回到 `running`，确认退出就进入终态 | agent 与 coderd 断网时进程照跑，重连后继续（`C/agent/agent.go#L589`，退避 100ms 到 10s）。**agent 自己关闭时杀掉全部进程**（`C/agent/agentproc/process.go#L320-L323`） | daemon 重启后会话全部丢失（内存 `cmap`），文件还在；daemon 死掉后沙箱仍显示 `started` 好几分钟，`errorReason: null`（#5140） | **应修改**：区分两种情况。①**Node Unreachable、Agent 还活着**：进程继续跑，Agent 在内存里缓冲，重连后补发（与 Coder 相同，保留）。②**Agent 重启**：要么照 Daytona 给每个命令配一个沙箱内 shim，把输出和退出码写进文件，要么照 Coder 直接认损失。Phase 1 选后者：以 `node_agent_restarted` 结束，「`lost` 回到 `running`」这条路径删掉 |
| 33-6 | Control Plane / PG 是语义权威，Agent 只报告观测；Reconciler 由事件即时触发、周期扫描兜底，所有动作幂等 | jobreaper 周期扫描，用 advisory lock（`control-plane-operations-vendor-practice.md` §1b） | 对 Sandbox 正是这个形状：事件 `@OnAsyncEvent` 触发 `syncInstanceState`，外加每 10 秒一次的 cron 扫描 `pending=true`，按沙箱加 Redis 锁（`DT/apps/api/src/sandbox/managers/sandbox.manager.ts#L831-L885`、`#L1010-L1019`、`#L1120-L1160`） | **保留**：Daytona 是同构的先例。按 33-1、33-5 简化后，Exec 的对账只剩「终态确认」和「节点回来后核对」两件事 |
| 33-7 | 取消是持久意图；超时从 Provider 开始执行时计时；两者都先给 5 秒 grace 再强杀；终止确认前不报告完成 | 取消：先写 `canceled_at`。job 还没被领走时直接完成；已在跑时，`completed_at` 不写（*"If the job is running, don't mark it completed!"*，`C/coderd/workspacebuilds.go#L918-L932`），派生出 `canceling`。provisioner 从心跳响应得知取消，先发 SIGINT，超过 `ForceCancelInterval`（默认 10 分钟）后判失败（`C/provisionerd/runner/runner.go#L469-L510`、`C/provisionerd/provisionerd.go#L79-L80`）。脚本超时：先 interrupt，几秒后强杀（`C/agent/agentscripts/agentscripts.go#L247-L250`） | **没有逐命令的取消**，只有删除整个 session：SIGTERM，默认等 5 秒，再 SIGKILL（`DT/apps/daemon/pkg/session/delete.go#L18-L67`、`DT/apps/daemon/cmd/daemon/config/config.go#L23`）。`exec` 超时直接 SIGKILL 进程组，没有 grace（`DT/apps/daemon/pkg/toolbox/process/execute.go#L83-L87`） | **保留**：与 Coder 同构（持久取消、canceling、先优雅后强制），5 秒与 Daytona 默认一致 |

## 2. 我们与两家不同的地方：他们为什么没那样做

### 2.1 「Exec 是 Control Plane 里的持久意图」（33-1）

- **一手理由：未找到。** 两家的文档、源码注释、issue 里都没有讨论过「要不要把命令持久化到控制面」。
- **两家各自持久化在哪一层（一手）**：Coder 用 `provisioner_jobs`（`C/coderd/database/dump.sql#L2964-L3001`）；Daytona 用 Sandbox 的 `desiredState` 加 cron 对账（`DT/apps/api/src/sandbox/managers/sandbox.manager.ts#L831`）。命令执行在两家都属于「到达 agent/daemon 后的数据面调用」。
- 【推断】两家都把「命令」看成交互式 IDE 或 SDK 调用的一部分：调用方在线、结果当场拿走，丢了就重跑。Coder 的主要用户是 IDE 里的人；Daytona 的 `exec` 默认超时 10 秒，就是给短命令准备的。
- **支持我们更重一点的一手证据（两家踩过的坑）**：
  - Daytona #4520：*"`POST /process/session/{id}/exec` returns **202 Accepted** but the command never runs"*，根因之一是 *"No shell liveness detection"*（<https://github.com/daytonaio/daytona/issues/4520>；修复 PR #4521 在冻结的公开仓库里没有合并）。我们的 Exec 只有在 Provider 确认启动后才进入 `running`，正好防住这一条。
  - Daytona #5140：daemon 被 OOM 杀掉后，*"the sandbox is left in a zombie `started` state for several minutes … with `errorReason: null`"*（<https://github.com/daytonaio/daytona/issues/5140>）。我们的 Execution Result 区分平台原因和退出码，防住这一条。
  - Daytona #5144：*"timeout returns an error and discards output emitted before expiry"*（<https://github.com/daytonaio/daytona/issues/5144>）。我们的日志按序号持久化，与超时结果分开，防住这一条。
  - Coder 也在往这个方向走：它为 AI agent 写的 `chatd` 引入了 *"an unlogged chat_heartbeats table for ownership leases"* 和版本化的状态机（`C/coderd/database/migrations/000519_chatd_core_state_machine.up.sql#L1-L10`，处于 `coderd/x` 实验目录）。也就是说，在「Agent 原生」的场景下，Coder 自己也把执行状态放进了控制面。
- **结论**：保留 Exec 资源。但「持久」只需要做到 Coder provisioner job 那一档（一行记录加时间戳派生状态），用不着 Attempt。

### 2.2 ExecAttempt、自动重试、`lost` 的恢复（33-1、33-4、33-5）

- **一手理由（不自动重试）**：Coder 的 *"so the end user can retry if they want to"*（`C/coderd/provisionerdserver/provisionerdserver.go#L550-L553`）。jobreaper 对卡住的 job 直接写失败日志并结束，不重派（`C/coderd/jobreaper/detector.go#L44-L52`）。
- **一手理由（Agent 退出就杀进程）**：Coder `agentproc` 的注释 *"Close kills all running processes and prevents new ones from starting"*（`C/agent/agentproc/process.go#L320-L323`）。Daytona 没有从磁盘恢复会话的代码路径（`daytona-sandbox-runtime-semantics.md` §4.6，【推断】）。
- **Daytona 留给想恢复的人的形状**：命令输出和退出码写成文件，由沙箱内的 wrapper 写入，不经 daemon 进程的管道（`DT/apps/daemon/pkg/session/execute.go`，见既有调研 §4.2）。我们如果将来要做「Agent 重启后接管 Exec」，这是唯一被验证过的做法。
- 【推断】我们的 Sandbox 被 ADR 绑定在一个 Node 上，又明确「不跨 Node 重调度」，所以 Attempt 只剩一个用途：区分「确认没启动、可以再投」和「可能启动了」。用 Exec 上的 `started_at` 是否为空就能表达。

### 2.3 Node Agent 单流承载数据帧（31-5）

- **一手**：Coder 的 agent RPC 是 yamux 多路复用的 dRPC，**每个 RPC 各占一条 yamux stream**（`C/coderd/workspaceagentsrpc.go#L107-L111`）。PTY 和 SSH 走 tailnet，不走这条 RPC 通道。Daytona 的 PTY 广播在客户端缓冲满时 *"drop the client"*（`DT/.../pty/websocket.go#L98-L117`）。两家都没有把高频字节流和控制消息放在同一个有序流里。
- 理由：**未找到一手陈述**。【推断】同一条有序流里，一个大的输出帧会排在心跳和取消命令前面（队头阻塞），而 gRPC/HTTP/2 的逐 stream 流控本来就能免费解决这个问题。

### 2.4 PTY：单控制者、输出进 PG、没有空闲回收（33-10）

- 单控制者：两家都是多写者。**未找到一手理由**说明他们为什么不限制。【推断】IDE 场景下多个窗口同时打字是用户自己造成的，平台不仲裁。我们的「Agent 加人类」同时 attach 的担忧是真实的，但 Phase 1 用「最后 attach 的连接控制」就够了。
- 输出进 PG：两家都不持久化 PTY 输出。Coder 用 64 KiB 环形缓冲，甚至承认它有 bug，更推荐 `screen`（`C/agent/reconnectingpty/reconnectingpty.go#L102-L104`）。【推断】PTY 字节流里大部分是重绘和控制序列，存下来对续传几乎没有价值，却会让日志上限很快触顶。
- 空闲回收：Coder 写明 *"Timeout describes how long to keep the pty alive without any connections. Once elapsed the pty will be killed."*（`C/agent/reconnectingpty/reconnectingpty.go#L93-L96`）。我们只写了「普通断开不终止」，没写「没人回来怎么办」。在 GPU 节点上，这意味着孤儿 shell 会一直占着 Sandbox。

### 2.5 「手写 OpenAPI」（31-1）

- 两家都是代码优先（Coder：swaggo 读 handler 注释；Daytona：NestJS 的 `SwaggerModule.createDocument`）。**未找到**任何一家讨论过规范优先和代码优先的一手理由。【推断】单团队用 Go，两种做法都有现成工具（swaggo 或 oapi-codegen），差别只在开发流程。用 ADR 锁死「手写」没有收益。
