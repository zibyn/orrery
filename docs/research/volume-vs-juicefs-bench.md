# 卷与 JuiceFS 在 AI coding 负载下的对比

调研日期 **2026-11-18**，commit `4eecdeb`。问题：ADR-0031 的卷（`orrery-resourcefs` 的可写挂载，runtime.md §17）和 JuiceFS 比，性能差多少，瓶颈在哪里。工具和原始输出在 `volume-bench/`。

## 1. 方法

- **机器**：16 核、30 GiB 内存、NVMe（ext4）；Linux 7.0。
- **对象存储**：本机的 RustFS（Docker，host 网络），卷和 JuiceFS 共用。没有真实的网络 RTT，所以对两边都偏乐观。
- **目标**：
  - 本地盘（基线）；
  - 卷，每 10 秒提交一次 / 每 60 秒提交一次（生产配置）；
  - JuiceFS 1.2.3 默认配置，元数据放在 Redis 7.4；
  - JuiceFS `--writeback`。
- **卷的提交**按 Agent 的 `commitVolumeOnce` 实现：seal → 逐个用预签名 PUT 上传待提交对象 → PUT Generation manifest → `VolumeCommitted`。和生产环境的差别有两处：没有 Control Plane（因此每次都上传全部待提交对象），也没有 `CommitGeneration`。
- **负载**（`bench.py`）：

  | 维度 | 内容 |
  |---|---|
  | 获取代码 | `git clone` orrery |
  | 安装依赖 | 解出真实的 `web/node_modules`（22,622 个文件，514 MiB）；`python -m venv` 带 pip |
  | 检索 | `rg`，冷缓存和热缓存各一次 |
  | 构建与测试 | `go build ./...`（冷构建、增量构建）、`go test`；`tsc --noEmit`、`vite build` |
  | Agent 编辑 | 200 次"读文件 → 写临时文件 → rename → `git status`"，最后提交 |
  | Git 操作 | status、checkout、`log -p`、`gc` |
  | 小文件 | 2 万个 4 KiB 文件 |
  | 数据库 | SQLite 逐条事务提交 |
  | 大文件 | 4 GiB 顺序读写；8 路各 512 MiB 并发读写；跨提交点追加 6 × 1 GiB |
  | 清理 | 删除整个仓库 |

  每个阶段运行时，另有一个**探针**每 10 ms 做一次 open+write+close，记录 p50、p99 和最大值。最大值就是终端或编辑器会感觉到的最长停顿。
- 每组只跑一次。

## 2. 结果

编码流程总耗时，指 clone、依赖、venv、检索、构建、编辑、Git、清理这几项相加：

| 本地盘 | 卷 60s | 卷 10s | JuiceFS wb | JuiceFS 默认 |
|---|---|---|---|---|
| 35s | **47s** | 71s | 415s | 895s |

| 指标 | 本地盘 | 卷 60s | JuiceFS 默认 | JuiceFS wb |
|---|---|---|---|---|
| git clone | 0.6s | 1.5s | 90s | 41s |
| 解出 node_modules | 0.6s | 5.0s | 489s | 92s |
| rg 全量，冷缓存 / 热缓存 | 0.36 / 0.03s | 2.8 / 0.37s | 6.8 / 4.8s | 10.8 / 6.8s |
| go build，冷 / 增量 | 13.1 / 1.1s | 13.3 / 1.6s | 93 / 7.3s | 75 / 8.1s |
| tsc / vite build | 2.8 / 4.5s | 3.5 / 4.6s | 20 / 30s | 22 / 27s |
| Agent 单次编辑，p50 / p99 | 2 / 103ms | 10 / 86ms | 57 / 786ms | 176 / 1302ms |
| 小文件创建 / 读（个每秒） | 71k / 188k | 8.9k / 14.5k | 43 / 4.4k | 1.8k / 5.9k |
| SQLite 事务每秒，rollback journal / WAL | 129 / 255 | 55 / 145 | 12 / 47 | 224 / 1092¹ |
| 顺序写 / 冷读（MiB/s） | 1283 / 1278 | 366 / 305 | 478 / 882 | 1155 / 1639 |
| 8 路并发写 / 读（MiB/s） | 407 / 3967 | 995 / 243 | 219 / 1558 | 4414¹ / 3450 |
| 探针最长停顿 | 209ms | 7979ms | 9153ms | 2079ms |
| 一次提交，对象数 / 数据量 / 耗时 | — | 28,554 / 995 MiB / **6m27s** | — | — |

## 3. 结论

1. **主流程上，卷比 JuiceFS 快一个数量级，接近本地盘。** JuiceFS 慢在两处：每个元数据操作都要访问 Redis，close 和 fsync 时还要同步上传到 S3。小文件密集的负载（依赖安装、clone、Go 构建缓存）最吃亏，开了 writeback 也还慢 4–18 倍。卷的元数据在内存里，写只落本地盘，这正是 ADR-0031 单写者模型带来的收益。
2. **卷的整个挂载会卡住几秒。** 有两个来源，都来自 runtime.md §17 的“写入和提交在同一把锁下串行”：
   - seal 持锁对脏集合做哈希：约 480 MiB、2.7 万个文件时要 4s，探针卡了 3.9s；
   - `Fsync` 持锁做 `fsync(2)`：对 4 GiB 文件 fsync 时，探针卡了 8s。

   这期间对其他文件的 open 也会卡住。
3. **卷的提交上传太慢。** Agent 逐个对象串行上传，每秒约 80 个对象，一次提交要 6–7.5 分钟。整轮测试只完成了 1 次提交。这期间丢失 Node，数据就丢了；Stop 也要等这么久。
4. **卷的并发读被串行化。** 写缓存里的文件，`Read` 持锁做 `pread`，8 路并发读只有 243 MiB/s，本地盘是 3967 MiB/s。
5. **跨提交追加的大文件每次都要整份重拷。** seal 之后写缓存被删掉，下一次写要把整个文件复制回来。追加测试里，跨过提交点的那一轮从 1.5s 涨到 8–9s。
6. **持久性承诺不同。** JuiceFS 默认在 fsync 返回时数据已经在 S3；卷的 fsync 只保证落到 Node 本地盘。卷的速度有一部分是靠推迟持久化换来的，第 3 点会把这个窗口拉长到好几分钟。

## 4. 没测的

- 换 Node 之后从 S3 懒加载冷读（已提交的块在同一次运行里都在本地块缓存中）。
- 真实网络下的对象存储延迟。
- 多次运行的方差。
