# 卷与 JuiceFS 在 AI coding 负载下的对比

调研日期 **2026-11-18**，commit `4eecdeb`。问题：ADR-0031 的卷（`orrery-resourcefs` 的可写挂载，runtime.md §17）和 JuiceFS 比，性能差多少，瓶颈在哪里。工具和原始输出在 `volume-bench/`。

## 1. 方法

- **机器**：16 核、30 GiB 内存、NVMe（ext4）；Linux 7.0。
- **对象存储**：本机的 RustFS（Docker，host 网络），卷和 JuiceFS 共用。没有真实的网络 RTT，所以对两边都偏乐观。
- **目标**：
  - 本地盘（基线）；
  - 卷，每 10 秒提交一次 / 每 60 秒提交一次（生产配置）；
  - JuiceFS 1.2.3 默认配置，元数据放在 Redis 7.4；
  - JuiceFS `--writeback`。
- **卷的提交**按 Agent 的 `commitVolumeOnce` 实现：seal → 逐个用预签名 PUT 上传待提交对象 → PUT Generation manifest → `VolumeCommitted`。和生产环境的差别有两处：没有 Control Plane（因此每次都上传全部待提交对象），也没有 `CommitGeneration`。
- **负载**（`bench.py`）：

  | 维度 | 内容 |
  |---|---|
  | 获取代码 | `git clone` orrery |
  | 安装依赖 | 解出真实的 `web/node_modules`（22,622 个文件，514 MiB）；`python -m venv` 带 pip |
  | 检索 | `rg`，冷缓存和热缓存各一次 |
  | 构建与测试 | `go build ./...`（冷构建、增量构建）、`go test`；`tsc --noEmit`、`vite build` |
  | Agent 编辑 | 200 次"读文件 → 写临时文件 → rename → `git status`"，最后提交 |
  | Git 操作 | status、checkout、`log -p`、`gc` |
  | 小文件 | 2 万个 4 KiB 文件 |
  | 数据库 | SQLite 逐条事务提交 |
  | 大文件 | 4 GiB 顺序读写；8 路各 512 MiB 并发读写；跨提交点追加 6 × 1 GiB |
  | 清理 | 删除整个仓库 |

  每个阶段运行时，另有一个**探针**每 10 ms 做一次 open+write+close，记录 p50、p99 和最大值。最大值就是终端或编辑器会感觉到的最长停顿。
- 每组只跑一次。

## 3. 结论

1. **主流程上，卷比 JuiceFS 快一个数量级，接近本地盘。** JuiceFS 慢在两处：每个元数据操作都要访问 Redis，close 和 fsync 时还要同步上传到 S3。小文件密集的负载（依赖安装、clone、Go 构建缓存）最吃亏，开了 writeback 也还慢 4–18 倍。卷的元数据在内存里，写只落本地盘，这正是 ADR-0031 单写者模型带来的收益。
2. **卷的整个挂载会卡住几秒。** 有两个来源，都来自 runtime.md §17 的“写入和提交在同一把锁下串行”：
   - seal 持锁对脏集合做哈希：约 480 MiB、2.7 万个文件时要 4s，探针卡了 3.9s；
   - `Fsync` 持锁做 `fsync(2)`：对 4 GiB 文件 fsync 时，探针卡了 8s。

   这期间对其他文件的 open 也会卡住。
3. **卷的提交上传太慢。** Agent 逐个对象串行上传，每秒约 80 个对象，一次提交要 6–7.5 分钟。整轮测试只完成了 1 次提交。这期间丢失 Node，数据就丢了；Stop 也要等这么久。
4. **卷的并发读被串行化。** 写缓存里的文件，`Read` 持锁做 `pread`，8 路并发读只有 243 MiB/s，本地盘是 3967 MiB/s。
5. **跨提交追加的大文件每次都要整份重拷。** seal 之后写缓存被删掉，下一次写要把整个文件复制回来。追加测试里，跨过提交点的那一轮从 1.5s 涨到 8–9s。
6. **持久性承诺不同。** JuiceFS 默认在 fsync 返回时数据已经在 S3；卷的 fsync 只保证落到 Node 本地盘。卷的速度有一部分是靠推迟持久化换来的，第 3 点会把这个窗口拉长到好几分钟。

### 4.2 对照 spec #295 的预期

| 预期（spec #295 “Expected effect”） | 结果 | 结论 |
|---|---|---|
| 探针停顿从几秒降到几十毫秒 | 卷 60s：7979 → 421ms；卷 10s：8392 → 800ms；不提交：30ms。在只跑追加的诊断里，seal 一个几 GiB 的文件时：18,148 → 204ms | 秒级停顿没有了；提交进行时还有几百毫秒 |
| 提交上传从几分钟降到几十秒 | 6m27s → 2m51s；7m35s → 2m0s | **没达到**，只快了 2.3–3.8 倍 |
| 写缓存文件的 8 路并发读接近本地盘 | 卷 60s：243 → 1478；卷 10s：379 → 2871；不提交：4437。本地盘 3253 | 不提交时达到；提交进行时达不到 |
| 跨提交那一轮追加回到约 1.5s | 诊断里跨 seal 的那一轮：13.8s → 16.9s / 9.6s | **没达到** |

**探针还有几百毫秒。** 这已经和树锁无关：不提交时最长 30ms，同一轮的本地盘自己在 8 路并发读写时也停过 1239ms。剩下的停顿都发生在提交进行时，有两个来源：

- **探针文件排在哈希队列里。** 探针每 10ms 重写一次 `.probe`，所以每次 seal 都会冻结它，而写冻结文件要等它哈希完。seal 按目录树的顺序把文件交给 8 个哈希 worker，`.probe` 要排在前面的文件后面，比如上一次提交之后 go build 写下的几千个 `.gocache` 文件。卷 10s 的 800ms 出现在第二次 seal（8.1s）和 `seqio` 重叠的时候。#302 去掉了这种排队，同一处降到 74ms（见 §4.5）。
- **上传抢盘。** 卷 60s 的 421ms 出现在追加阶段。那时没有 seal，只有上传在跑（见 §4.4）。

**提交只快了 2.3–3.8 倍，瓶颈是本机的 RustFS，不是 Agent。**

- 单独压测 RustFS（16 KiB 对象，`after-diag.txt`）：1 路每秒 56 个，20 路 425 个，64 路反而降到 231 个。20 路时 RustFS 只用了 0.7 个核，瓶颈不在 CPU，应该在盘上：每个对象都要 fsync。
- 跑负载时，前台和 RustFS 抢同一块盘，提交只有每秒 167–228 个对象。要做到“几十秒”，每秒得上千个对象，同机单盘的 RustFS 给不出来。换成能承受更高并发 PUT 的对象存储，收益应该更大，但这次没测。
- 连接复用不是原因。#298 提到 `publishHTTP` 每个 host 只保留 2 个空闲连接。同样提交约 2.5 万个对象，把 `MaxIdleConnsPerHost` 调到 20 后每秒 173 个，不调每秒 163 个，没有差别，所以没改。这两次是在机器有别的负载时跑的，绝对值偏慢。

**提交进行时，并发读达不到本地盘。** #296 之后，读只拿文件自己的内容锁（共享），不提交时 8 路读能到 4437 MiB/s。提交时有两件事挡它：

- **seal 哈希一个文件时，独占这个文件的内容锁**，所以同一文件的读也要等它哈希完。卷 10s 的第二次 seal 正好在哈希 `seqio` 刚写完的 4 GiB 文件，那一轮冷读只有 429 MiB/s，不提交时是 1375。写入本来就会因为文件被冻结而等待，哈希其实可以只拿共享锁。
- **上传抢盘**（见 §4.4）。卷 60s 的 8 路读（1478）和顺序冷读（107）都落在上传期间，当时没有 seal。

**跨提交追加没有回到 1.5s。** 先更正 §3 第 5 点：基线每轮只完成了 1 次提交，在第 10 / 60 秒开始，所以追加阶段其实没有跨过 seal。那几轮跑到 8–9s，是因为它们和上传同时进行。这次复测的追加阶段同样没跨 seal，13.6s 和 14.3s 那几轮也落在上传期间。

为了真正测跨提交，诊断运行只跑追加，每 10 秒提交一次，新旧代码各跑一遍：

| | 每轮耗时（s） | 三次 seal 耗时 | 探针最长停顿 |
|---|---|---|---|
| 前（`4eecdeb`） | 1.2 / 1.1 / 3.7 / 13.8 / 4.8 / 1.2 | 1.8 / 14.6 / 13.2s | 18,148ms |
| 后 | 1.1 / 1.4 / 2.3 / 1.3 / 16.9 / 9.6 | 1.7 / 3.1 / 16.4s | 204ms |

seal 之后不再整份复制，探针也不卡了，但跨 seal 的那一轮仍要 10–17s。原因是 seal 每次都把整个文件重读一遍、算哈希，再把每个块写进 `objects/`，约 5 GiB 时要 16s，文件越长越慢。写冻结文件要等这一步做完；做完之后，这几个 GiB 的写回还要和追加抢盘。要回到 1.5s，有两种办法：

- seal 只处理上次 seal 之后改过的块，没改的块沿用已有摘要，也不再写对象；
- 写冻结文件时不必等哈希。

这两种都不在 spec #295 的范围里。

### 4.3 #296、#297、#298 各自带来的变化

- **#296：内容 IO 不再持树锁。** 读、写、`fsync` 只拿自己 inode 的锁。
  - `fsync` 不再挡别的文件：卷 60s 的 `seqio` 阶段要对 4 GiB 文件 fsync，探针最长停顿 7979 → 108ms，不提交时只有 4ms。
  - 8 路并发读不再串行：不提交时 4437 MiB/s，基线只有 243。
- **#297：seal 离开树锁，seal 后保留干净副本。**
  - seal 不再冻住整个挂载：
    - 卷 10s 的第一次 seal 落在检索阶段，探针 3918 → 69ms；
    - 卷 60s 的 seal 落在 SQLite 阶段，3807 → 198ms；
    - 追加诊断里 seal 一个几 GiB 的文件，18,148 → 204ms。
  - seal 之后写缓存还在，下一次写不再复制整个文件。但写冻结文件、读正在哈希的文件，都要等这个文件哈希完（见 §4.2）。
- **#298：并发上传。** 一次提交从 6m27s 降到 2m51s（卷 60s），从 7m35s 降到 2m0s（卷 10s）。上限是本机 RustFS（见 §4.2）。副作用是在 bench 里，20 路上传期间编码流程慢了一倍多（见 §4.4）。

### 4.4 提交和前台抢盘

不提交的那次运行里，卷几乎没有停顿（30ms），SQLite、顺序读写、追加都接近本地盘。一旦提交开始在后台上传，前台的 fsync 和冷读就慢下来：

- 卷 60s 上传期间，顺序冷读 1375 → 107 MiB/s，SQLite WAL 252 → 47，追加有两轮跑到 5.8s 和 14.3s；
- 卷 10s 的编码流程被上传压着，比基线还慢 26s。

为了分清拖慢前台的是 seal、上传，还是上传的并发，又跑了三组诊断：

- **只 seal，不上传**：每 10 秒 seal 一次，对象不离开 Node。编码流程 43s，和不提交时（42s）一样，说明 seal 本身不拖慢编码流程。
- **整轮卷 10s，1 路上传**：编码流程 44s，和不提交时一样，20 路时却是 97s。三项对比如下（1 路对 20 路）：go build 冷构建 14.6s 对 21.4s，tsc 3.0s 对 13.1s，`git log -p` 1.2s 对 14.4s。
- **同一组阶段，20 路对比 1 路上传**：阶段是 clone、解出 node_modules、SQLite、顺序读写、追加，每 10 秒提交一次。

| | SQLite rollback / WAL | 顺序写 / 冷读（MiB/s） | 追加每轮（s） | 提交总耗时 |
|---|---|---|---|---|
| 不提交（整轮运行） | 82 / 252 | 943 / 1375 | 1.4/1.5/1.4/1.3/1.3/1.9 | — |
| 1 路上传 | 41 / 126 | 319 / 129 | 1.3/1.3/1.4/1.4/8.2/1.2 | 5m57s |
| 20 路上传 | 30 / 128 | 756 / 95 | 5.1/1.4/1.4/1.4/1.4/8.0 | 2m10s |

两类负载受的影响不同：

- **fsync 和大文件冷读**：只要在上传就会变慢，1 路和 20 路差不多，20 路只是把这段时间从 6 分钟缩到 2 分钟；
- **编码流程**（go build、tsc、`git log -p`）：1 路上传时没有影响，20 路时慢了一倍多。

bench 里 RustFS 和卷的写缓存在同一块 NVMe、同一个 ext4 上。RustFS 每存一个对象都要 fsync，20 路时每秒约两百次，前台的 fsync、冷读和元数据操作都要排在这些 fsync 后面。

生产上，对象存储不在 Node 的盘上，大部分影响应该不会出现。但还有两点 bench 测不出来：

- Node 上仍有上传时读 `objects/` 的 IO；
- bench 的上传和 FUSE 守护进程在同一个进程里，生产上上传在 Agent 进程里。

所以 20 路上传会不会拖慢前台，要在接真实对象存储的 Node 上确认。

### 4.5 #302：写冻结文件时先处理它

#302 之后，写一个冻结文件时，如果还没有 seal worker 开始处理它，写入方就自己先处理这一个文件，不再排在整个脏集合后面；已经在处理的，照旧等它处理完。每个文件仍只处理一次，manifest 里仍是 seal 那一刻的内容。

复测在 2026-11-19，用同一台机器、同一个 RustFS，代码是 `feat/302-frozen-write-first` 的 `6e1b377`，只跑卷 10s 和卷 60s 两组。原始输出在 `volume-bench/after-302-s3.txt`。

探针最长停顿（“前”是 §4.1 的“后”）：

| | 卷 10s | 卷 60s |
|---|---|---|
| 整轮 | 800 → 419ms | 421 → 417ms |
| 和 seal 重叠的阶段 | 检索 69 → 21ms，`seqio` 800 → 74ms | SQLite 198 → 49ms |
| 整轮最长的那次在 | 追加，只有上传在跑 | 追加，只有上传在跑 |

- **和 seal 重叠时，探针停顿降到几十毫秒**，达到 spec #295 的预期。卷 10s 的第二次 seal 这次用了 14.9s，同样落在 `seqio` 上，探针最长只停了 74ms。
- **整轮的最长停顿现在都在追加阶段，约 420ms。** 那时 seal 已经结束，只有上传在跑。卷 60s 前后都是这样（421 → 417ms），所以这部分来自上传抢盘（§4.4），不是 #302 要解决的。本地盘自己在追加阶段也停过 275ms。

其他变化都在单次运行的噪声范围内：

- 编码流程：卷 10s 97 → 94s，卷 60s 50 → 42s。卷 60s 在第一次提交之前就跑完了，所以这 8s 和 #302 无关。
- 卷 10s 第二次 seal 处理的对象数和数据量都和上次一样（6,770 个、541 MiB），耗时却从 8.1s 变成 14.9s。原因没查；写入方先处理的只是它自己要写的那个文件，seal 的总工作量没有变。
- 提交总耗时：卷 60s 2m51s → 2m23s；卷 10s 两次提交 2m0s / 1m14s → 2m0s / 57s。

### 4.6 后续

- seal 只处理上次 seal 之后改过的块，没改的块沿用已有摘要，也不再写对象。这样大文件跨提交的那一轮就不会随文件变长而变慢。
- 哈希冻结文件时只拿共享锁，这样读不用等哈希。写入本来就因为文件被冻结而等待。
- 换一个不和写缓存共用一块盘的对象存储重跑一遍，量出 20 路上传的真实提交耗时，以及它对前台的影响。

## 5. 没测的

- 换 Node 之后从 S3 懒加载冷读（已提交的块在同一次运行里都在本地块缓存中）。
- 真实网络下的对象存储延迟。
- 多次运行的方差。从 §4 看，这台机器上单次运行的噪声很大：JuiceFS 代码没变，wb 模式从 415s 变成 149s。
